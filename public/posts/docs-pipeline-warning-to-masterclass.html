When a Single Warning Turned Into a Docs-as-Code Masterclass

Published 2026-01-06 · Tags: DevOps, Docs-as-Code, CI/CD, HTML, Automation

I spent this week refining the documentation pipeline for one of my projects — the kind of work that usually feels quiet and invisible, but ends up supporting everything else.

The goal sounded simple: lint Markdown, format everything consistently, validate links, validate generated HTML, and make sure the pipeline fails when something is wrong. In other words, treat documentation with the same discipline as production code.

Everything worked beautifully… except for one stubborn warning:

Raw ">" must be encoded as "&gt;"

One line. One symbol. But that warning ended up teaching me more than I expected about encoding, automation discipline, and docs-as-code workflows.

The Docs Tooling Stack

Here’s the tooling stack behind this particular docs pipeline:

  • markdownlint-cli2 — Markdown style & structure
  • Prettier — formatting for HTML/CSS/JS/JSON/YAML
  • linkinator — internal & external link validation
  • html-validate — standards-compliant HTML
  • npm scripts — the glue for the pipeline

The philosophy was simple: if something breaks, the CI should say so, loudly. And it did — very loudly — about a single >.

Hunting Down the Offending Character

I wanted to be sure this was a real problem, not noise, so I started by searching for raw > characters that were not part of HTML tags.

PowerShell
Bash
# PowerShell – find > that isn't part of <tags>
Select-String -Path .\tooling-setup.html -Pattern '(?<!<)>' -AllMatches
# Bash – rough equivalent
grep -RIn ">" tooling-setup.html | grep -v "<"

That surfaced exactly what I needed: raw text like Next: CI/CD Pipelines > — safe for browsers, but not for a strict HTML validator.

The Real Fix (Not a Hack)

Instead of blindly replacing every >, I fixed only the text that was truly raw: 

Next: CI/CD Pipelines &gt;

For shell redirection examples, I kept the command semantics but encoded the output operator in HTML:

PowerShell
Bash
# PowerShell
echo "npx lint-staged" `> .husky/pre-commit

# Bash
echo "npx lint-staged" > .husky/pre-commit

In the HTML docs, those become: 

echo "npx lint-staged" &gt; .husky/pre-commit

After a few careful edits, I re-ran the full pipeline and finally got the quiet CI I was looking for — 0 errors, 0 warnings from markdownlint, Prettier, linkinator, and html-validate.

What This Experience Reinforced

  • Documentation is engineering work. It deserves the same rigor as application code.
  • Warnings are invitations. Suppressing them is fast; understanding them is growth.
  • Automation doesn’t replace thinking. It forces better thinking.
  • Quiet CI is healthy CI. Noise trains teams to ignore real problems.
My rule going forward: fix the root cause. Don’t teach your tools to ignore you. One warning today can become ten bugs tomorrow.

Final Thoughts

This wasn’t really a story about a > symbol. It was a story about quality culture, craftsmanship, docs-as-code discipline, and respecting the feedback loops that CI gives us.

If you’re building your own docs pipeline: enable HTML validation, don’t suppress the warnings, and follow the trail. You’ll always learn something — and that learning is worth documenting.
